# M4 — Proof

Branch: `m4-proof`. Spec: `docs/superpowers/specs/2026-10-11-omero-completion-design.md`, section 7, M4.

## What exists already

- `benchmark/retrieval_eval.py`: a 16-passage eval that needs `DATABASE_URL` (the owner's Neon database), so it is never run here.
- No hybrid retrieval. M1 deferred it to M4 so the evaluation decides.
- Deployment embeds with the `hashing` backend (no paid embedding API).
- Billing tests cover checkout, deletion and payment failure, but not webhook replay or out-of-order events.
- No Playwright. No restart test. No Postgres tests run anywhere (no local Postgres, Docker usually off).

## Work

1. **Hybrid retrieval.** `qa/lexical.py`: a BM25 scorer and reciprocal rank fusion (k = 60). `RETRIEVAL_MODE=vector|hybrid`.
   - In memory: BM25 over the tenant's chunks, fused with the cosine ranking.
   - Postgres: a second query with `websearch_to_tsquery('english', …)` against `to_tsvector('english', content)`, backed by a GIN expression index (migration `0014`), fused in Python. Same tenant, status, archive and scope filters as the vector query.
   - `similarity` stays the cosine score for every chunk, so nothing downstream changes meaning.
2. **Evaluation corpus and runner.** `services/api/eval/corpus.json`: about 30 short company documents (with near-miss distractors) and about 50 labelled questions, each with its relevant document and a fact phrase. `python -m omni_modal.benchmark.eval` ingests it through the real chunker and in-memory store, reports recall@1, recall@5 and MRR for vector versus hybrid on each available embedding backend, and checks citations through the real extractive answer path: every cited source is a relevant document, and the quoted snippet contains the fact. It writes `eval/results.json`. The default `RETRIEVAL_MODE` is whatever wins, and the README quotes the measured numbers.
3. **Cross-tenant coverage test.** Tenant A creates one of every resource. For every route with a path parameter, tenant B gets 403 or 404 and none of A's text. Any route not covered and not on a short exemption list fails the test, so new routes cannot skip it.
4. **Billing replay.** Processed Stripe event ids are recorded (in memory and Postgres, migration `0014`). A duplicate is ignored. A plan event older than the last one applied to the org is ignored. Tests cover upgrade, downgrade, cancellation, duplicate replay and out-of-order replay.
5. **Restart test (Postgres).** It runs only when `OMERO_TEST_DATABASE_URL` is set, never `DATABASE_URL`. It runs the migrations, creates a user, a document, a session, a project and a report, builds a fresh app, and checks that everything is still there. The Postgres store tests and the hybrid SQL use the same variable.
6. **Playwright journey.** `apps/web/e2e/journey.spec.ts`: sign up, upload, watch processing, ask, see a cited answer, save to a project, generate a report. Playwright starts the API in memory (`OMERO_DISABLE_DOTENV=1`, throwaway JWT secret) and the built frontend. Locally it uses the installed Chrome. In CI it uses Playwright's Chromium.
7. **CI.** Add a Postgres job (`pgvector/pgvector:pg16` service, migrations, Postgres tests), an eval job that fails if recall drops below the committed results minus a margin, and an e2e job.
8. **Operations.** Add a backup and recovery section to `docs/operations.md`: what Neon keeps, how to restore, re-running migrations, rebuilding chunks by reprocessing, and S3 versioning.

## Decisions

- The eval runs in memory so anyone can reproduce it with no keys or database. The Postgres eval stays as an optional check against a disposable database.
- No new embedding provider in M4. A hosted free embedding backend is a candidate for M5 if the eval shows hashing plus BM25 is still weak.
- Tests never read `DATABASE_URL`.

## Outcome (2026-10-18)

- Hybrid retrieval is on by default. Measured: with hashing embeddings, recall@1 rose from 0.589 to 0.768 and MRR from 0.681 to 0.839. With MiniLM, recall@1 rose from 0.786 to 0.821 and recall@5 fell by one question.
- "Supported citation" (the quoted snippet contains the fact) is 0.71 on the deployed setup. The extractive path picks the quoted sentence by word overlap. This is recorded as a known gap and is an M5 candidate.
- Found by the new tests and fixed:
  - `0002_perf.sql` could not run on an empty database (`ALTER DATABASE current_database()`), so no fresh database could be built from the migrations. It now uses a `DO` block. All 14 migrations apply to an empty pgvector database.
  - The rate limit (20 requests a minute per user, on every request) blocked a new user within their first minute. It is now split: 300 a minute for ordinary requests, and 20 for questions, the assistant and uploads.
  - The pgvector retriever read the query cache but never wrote to it.
  - `/entities/{id}` answered 200 for another tenant's document id (with no data). It now answers 404.
  - `.env.example` and the Drizzle schema said 1536 embedding dimensions; the database column is 384.
- Not done: a reranker (no measurement yet), and the browser test covers only the main journey.
